### B2, nested control move and clone do not validate destination placement

`crates/rdocx/src/content_control.rs:1693`
`crates/rdocx/src/content_control.rs:1721`
`crates/rdocx/src/content_control.rs:2815`

The nested paths select a destination from its location and insert the source shell bytes directly. Neither path compares the source content grammar with the destination parent. For example, a valid row control containing `w:tr` can be cloned into a paragraph location, producing a paragraph-owned control with row content. An inline control can likewise be inserted into a table. These operations bypass the placement checks used during creation and the content checks used by unwrap.

Reopening is not schema validation here. `parse_content` preserves children outside the current owner grammar as raw content at `crates/rdocx-oxml/src/content_control.rs:2057`. That preservation behavior must not authorize creation of invalid structure. Enforce the actual destination grammar before publication for both move and clone. Add mismatched row, cell and inline cases that assert refusal and unchanged package bytes, alongside valid same-placement cases. The existing lifecycle test at `crates/rdocx/tests/integration_test.rs:26110` exercises compatible block and inline destinations only. This violates the placement and atomic refusal contract at `.claude/plans/F-285-design.md:40`.

### B3, Python cannot move or clone content controls through the promised lifecycle API

`crates/rdocx-py/src/document.rs:11648`
`crates/rdocx-py/src/document.rs:7076`
`crates/rdocx-py/python/rdocx/_rdocx.pyi:1343`

Rust adds `move_content_control` and `clone_content_control`, but Python exposes neither location-aware wrapper. Its existing `clone_content` and `move_content` call `direct_content_index`, which accepts only Paragraph or Table handles, and require an integer body destination. A frozen ContentControl snapshot or ContentLocation cannot reach either native operation. Row, cell and inline controls therefore have no public Python move or clone path.

F-285 explicitly promises the same document methods in Python at `.claude/plans/F-285-design.md:38`, including the nested lifecycle wrappers described at line 36. Expose the location-addressed operations, update the stub, and verify compatible moves and clones, identity handling, stale-location refusal and atomic invalid-destination refusal in Python. The prefix checkpoint is valid process state, but it does not waive this final contract gap.

### B4, custom XML creation checks element counts but does not validate attributes

`crates/rdocx/src/content_control.rs:1829`
`crates/rdocx/src/content_control.rs:1838`
`crates/rdocx/src/bibliography.rs:1859`

`validate_store_item` discards Start and Empty payloads without consuming their attribute iterators. The quick-xml event reader does not itself validate those attributes. Thus an input such as `<root a="1" a="2"/>` passes the one-root and depth checks even though duplicate attributes make it ill-formed XML. The staging helper then stores the original bytes. Package serialization's XML character check does not reject duplicate attributes, and this custom item is not a modeled Word story that would supply the missing validation.

This contradicts the one well-formed element contract at `.claude/plans/F-287-design.md:31`. Validate attribute syntax and uniqueness, together with the rest of XML well-formedness, before allocating or publishing the store. Retain valid input bytes verbatim. Add duplicate-attribute and malformed-attribute refusals with unchanged package bytes. Current A1 inputs at `crates/rdocx/tests/integration_test.rs:26903` cover empty bytes, multiple roots and an unfinished start tag, which do not distinguish this faulty validator.
